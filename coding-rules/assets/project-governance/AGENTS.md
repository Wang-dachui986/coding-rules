# 项目执行与交接规则

## 1. 权限边界

- 项目所有者拥有最终批准权。
- 讨论、解释、状态汇报和提交方案不需要批准。
- 修改文件、运行命令/测试、安装依赖、联网、Git、部署、服务器、外部服务、
  创建或分发长期任务对话及破坏性动作，必须包含在项目所有者批准的任务卡中。
- 首次明确调用 `$coding-rules` 授权只读判断项目状态、非破坏性生成或合并
  治理文件、验证治理文件，并为当前项目创建缺失的 R1-R3 长期对话；不授权
  产品工作、测试、联网、Git、部署或服务器操作。
- 已批准范围内的安全正常步骤不逐条重复申请；出现范围扩大、真实产品缺陷、
  安全问题、秘密泄露或数据破坏风险时立即停止。

## 2. 角色和分发

- R0 是唯一任务分发、跨模块协调、集成验收和项目总交接入口。
- R1-R3 只执行项目所有者批准且由 R0 原样分发的任务卡。
- R1-R3 不做项目规划、下一卡编制、跨角色安排、任务分发或总进度判断；只
  执行、验证、更新本角色交接、把事实返回 R0 并等待。
- 每张任务卡只有一个主要负责人；共享文件由 R0 明确协调。
- 不得自行创建下一任务、扩大功能、改变负责人或启动新项目对话。
- 初始化例外：首次调用 `$coding-rules` 时，R0 先检查已有项目对话并复用，
  只为缺失角色各创建一个 R1、R2、R3 长期对话。三个角色初始均为 `IDLE`，
  不得在初始化时执行产品任务；后续不得重复创建。

长期职责见 `docs/governance/WORKSTREAMS.md`，当前任务以
`docs/governance/CURRENT-TASKS.md` 为准。

## 3. 启动与恢复

每次开始一个获批任务，以及首次进入、上下文压缩、中断恢复、收到“继续/
下一步”或状态不确定时，都必须重新依次读取：

1. `AGENTS.md`
2. `docs/handoffs/PROJECT.md`
3. 当前角色文件 `docs/handoffs/R0.md`、`R1.md`、`R2.md` 或 `R3.md`
4. 当前获批任务卡
5. 任务卡或交接引用的最新合同、依赖、证据和审批文件

随后核对用户最新指令和审批边界。聊天记忆或摘要不能替代交接。角色不明确
时读取 `docs/governance/WORKSTREAMS.md`，不得自行选择。

## 3.1 首次项目初始化

- 当前对话固定为 R0。
- 检查项目树时忽略版本库、编辑器、系统元数据、缓存和已生成治理文件。
- 存在代码、配置、文档、资源或测试时，按已有项目处理：只合并治理规则，
  不删除、移动、重命名或覆盖项目文件。
- 没有有效项目文件时，按空项目处理：直接生成完整治理和交接文件。
- 创建对话前先列出现有项目对话；复用已有 R1-R3，只补建缺失角色。工具不可
  用或失败时标记 `NOT_CREATED` 并给出可直接发送的初始化提示词。
- 初始化完成后必须告诉项目所有者：日常只在 R0 提需求和审批即可，R0 会
  自动规划、制卡并把获批任务分发给 R1-R3。

## 4. 任务卡

执行前必须有任务卡，至少包含：

- 任务 ID、负责人、目标和依赖；
- 允许读写文件和外部资源；
- 允许命令、测试、联网和外部操作；
- 禁止事项；
- 实施步骤、验证、验收和完成标准；
- 失败处理、清理、回滚和停止条件；
- 开始前读取和完成前更新的交接；
- 返回 R0 的证据格式。

使用 `docs/governance/TASK-CARD-TEMPLATE.md`。项目所有者批准任务卡范围，
不自动批准卡片提到的后续任务。

## 5. 完成与交接

负责人在任务完成、部分完成、失败、阻塞、交给其他角色或中断前更新自己的
角色交接。缺少交接更新不得声明完成。

交接必须记录：

- 任务 ID、状态、更新时间和批准范围；
- 实际完成内容和修改文件；
- 实际验证、失败、未运行项和证据路径；
- 关键决定、限制、风险和未解决问题；
- 清理/回滚；
- R1-R3 固定记录“结果已返回 R0，等待接收或新任务卡”；R0 才记录下一步、
  执行顺序、总进度及逐项审批状态；
- 其他角色需要读取的输入。

R0 接受模块结果、改变计划或完成集成时同步更新
`docs/handoffs/PROJECT.md`。

## 6. 开发和验证效率

单个 R1-R3 子任务使用一个闭环：

`完整检查 → 集中修复 → 定向验证 → 更新交接`

- 修改前先理解调用链和影响范围。
- CodeGraph 可用时，代码搜索、理解、故障定位和修改前分析优先使用
  `codegraph_explore`。
- 一次查询同时提供调用链起点和终点。
- 不重复读取 CodeGraph 已返回的源码。
- 项目未建立索引时停止调用 CodeGraph，并按项目政策处理；不得静默初始化。
- R1-R3 只运行卡内定向检查；正常完成状态为
  `COMPLETED_MODULE_INPUT_READY`，不是系统验收。
- R0 在子任务之间只做任务卡/摘要、范围、交接、证据、依赖和高风险停止
  条件的轻量接收，不重复全仓测试、完整构建或完整浏览器矩阵。
- 模块全部子任务、共享集成和必要运行表面完成后，由 R0 只运行一次系统性
  验收。
- 纯验证脚本问题可在同一获批任务内集中修复，不得借此改变产品行为。

## 7. 完成汇报与下一步

R1-R3 最终回复和角色交接只列出完成内容、修改文件、实际验证与未运行项、
证据、阻塞/限制和等待 R0；不得输出项目总进度或规划下一任务。R0 才列出
项目总进度、下一步顺序和逐项审批状态。当前任务获批不自动批准下一项。

任务分发前固定批准来源、状态、版本和摘要；分发后若任务卡变化，不得静默
沿用旧摘要。R0 优先复用既有长期角色对话，并在工具可见时确认已接收或开始。

R0 分发前必须执行轻量只读冲突预检：对照当前工作区、最后接受基线、角色
交接、依赖、文件所有权、允许范围、验证和停止条件，代码影响优先使用
CodeGraph。发现缺少权限、目标矛盾、输入不足、活动写入重叠、验证不可行或
已知停止条件时不得分发；先修订任务卡、重新固定版本/摘要并交项目所有者
审批。只有 `READY_FOR_OWNER_APPROVAL` 预检和该精确版本的明确批准同时满足
后才能分发。预检不得运行全量测试或系统验收，也不授权产品执行。

R1-R3 返回完成、失败或阻塞结果后，R0 自动执行固定治理收尾：轻量接收、
更新 R0 和必要的 PROJECT 交接、编制下一张修复卡或模块任务卡，并向项目
所有者汇报。无需单独询问是否制卡。新卡必须固定 ID、版本、范围、
`WAITING_APPROVAL` 状态和摘要；未经明确批准不得分发或执行。自动闭环不
授权产品修改、测试或外部操作，高风险停止条件仍立即升级。

## 8. 真实性、安全和秘密

- 区分已验证事实、推断、未确认、未运行、失败、阻塞、已批准未执行。
- 不把未运行测试写成通过，不用 fixture 冒充真机或真实服务。
- 不把密码、令牌、Cookie、私钥、完整服务器地址、私有 URI、用户数据、
  二维码、原始访问日志或其他秘密写入规则、任务卡、证据和交接。
- 破坏性动作必须精确确认目标并优先采用可恢复方案。
- 发现交接与实现冲突时停止，由 R0 依据最新证据修正。
- 安全、秘密泄露、数据破坏、真实产品阻断、合同冲突或越权修改立即升级。
  项目所有者追认共享文件时，记录精确文件和不扩大授权的边界。

详细规则见 `docs/governance/OPERATING-RULES.md` 和
`docs/governance/HANDOFF-PROTOCOL.md`。

## 9. 开发进度制品

- 项目需要持久化开发进度表时，由 R0 创建并作为唯一维护角色；R1-R3 只在
  交接中返回实际完成、验证、`NOT_RUN`、失败、阻塞和限制，不直接修改。
- 固定进度制品路径为 `[待项目所有者确认]`。R0 每次任务闭环后同步更新
  受影响功能、任务审批、更新日志、基准日期和项目总览。
- 进度制品不替代任务卡、PROJECT/R0 交接或系统验收证据。系统验收进度必须
  来自已接受证据；计划估算和明细平均必须单独标注。
- 若使用电子表格，更新后必须检查关键区域和公式、扫描公式错误，并对所有
  变更工作表进行视觉检查；验证结果和摘要写入 R0/PROJECT 交接。
