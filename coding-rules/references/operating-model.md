# 通用项目执行模型

## 1. 权力与职责

- 项目所有者：批准范围、风险、外部操作、版本发布和最终取舍。
- R0：需求收敛、任务卡、唯一分发入口、跨模块契约、集成验收和总交接。
- R1-R3：各自长期工作流的唯一实现责任人，不得自启下一任务。
- 评审者或短期子智能体：只完成边界明确的临时检查，不取得长期所有权。

项目所有者批准任务卡，不等于批准任务卡之外的下一阶段、发布、联网或服务
器操作。R0 接受结果，不等于替项目所有者批准业务决策。

## 2. 审批模型

无需审批：

- 解释、讨论、回答问题；
- 汇报已经验证的状态；
- 提交方案供审核。

调用 `$coding-rules` 本身只批准治理文件的读取、生成、合并和验证。

通常必须先审批：

- 修改产品、测试、脚本、依赖或配置；
- 执行命令、测试、构建、安装或格式化；
- 联网、Git、发布、部署、服务器和外部服务；
- 创建、分发或改变长期任务对话；
- 删除、覆盖、迁移或其他难恢复动作。

任务卡应一次性列明正常完成路径需要的安全动作，避免每条命令重复审批。
发现真实产品缺陷、安全风险、秘密泄露、数据破坏或范围扩张时立即停止。

## 3. 任务生命周期

```text
候选需求
  → R0 调查和拟定任务卡
  → 项目所有者批准
  → R0 原样分发
  → 负责人读取交接
  → 完整检查
  → 集中实现
  → 定向验证
  → 更新角色交接
  → R0 轻量接收为模块输入
  → 下一获批子任务
  → 共享集成
  → 一次模块系统性验收
  → 更新项目总交接
  → 项目所有者决定下一步
```

状态只使用：

`PLANNED`、`WAITING_APPROVAL`、`APPROVED`、`IN_PROGRESS`、
`COMPLETED_MODULE_INPUT_READY`、`COMPLETED_PENDING_REVIEW`、
`COMPLETED_ACCEPTED`、`BLOCKED`、`FAILED`、`SUPERSEDED`、`IDLE`。

## 4. 任务卡要求

每张任务卡必须包含：

1. 任务 ID、版本、负责人和目标；
2. 前置事实和依赖；
3. 允许读取、创建和修改的文件；
4. 允许执行的命令、测试、联网和外部操作；
5. 明确禁止事项；
6. 实施步骤和完成标准；
7. 定向验证和最终验收；
8. 失败、回滚、清理和停止条件；
9. 开始前读取的交接；
10. 完成前更新的交接；
11. 返回 R0 的证据格式；
12. 完成汇报、项目总进度、下一步顺序和逐项审批状态。

任务卡必须只有一个主要负责人。共享文件由 R0 协调，避免两个角色同时写入。
批准来源、行政状态、版本和固定摘要应在分发前完成；分发后改变卡片时不得
静默沿用旧摘要。

## 5. 多对话分发

- 长期对话按稳定模块划分，不按每个小功能新建。
- R0 保持唯一总控对话；模块对话只接收原样任务卡。
- 对话数量取决于真实并行边界。默认最多三个执行工作流，避免管理成本超过
  开发收益。
- 模块之间先冻结接口和文件所有权，再并行实现。
- 一个角色需要另一个角色输入时，向 R0 报告依赖，不直接扩大对方任务。
- R0 复核实际文件、测试、证据和交接，而不是只接受“已完成”口头声明。
- 优先复用既有长期角色对话；分发后在工具可见时确认目标对话已接收或开始。

## 6. 中断与上下文恢复

出现首次进入、上下文压缩、中断恢复、“继续/下一步”或状态不确定时：

1. 读取 `docs/handoffs/PROJECT.md`；
2. 读取当前角色文件；
3. 读取交接引用的最新任务卡和证据；
4. 核对用户最新指令和批准边界；
5. 继续、停止或只问一个会改变结果的关键问题。

聊天记忆和摘要不能替代交接文件。交接与实现冲突时停止，由 R0 根据最新
证据修正。

## 7. 开发和验收效率

- 修改前理解调用链和影响范围；CodeGraph 可用时优先使用。
- 同一模块先完成一次相关路径审计，批量列出问题。
- 在同一获批范围内集中修复验证脚本问题，不为每个脚本问题重新开任务。
- R1-R3 开发阶段只跑定向检查并更新交接，成功状态为模块输入就绪。
- R0 在子任务间只核对任务卡/摘要、范围、交接、证据、依赖和高风险停止
  条件，不重复全仓测试、完整构建或完整浏览器矩阵。
- 模块全部子任务、共享集成和必要运行表面完成后，只跑一次系统性验收。
- 全量失败后先批量诊断同类路径，不机械从头重跑。
- 小功能必须完整闭环后再进入下一项，避免多个半成品并行。
- 安全、秘密、数据破坏、真实产品阻断、合同冲突或越权修改立即升级；项目
  所有者追认共享文件时，记录精确文件和不扩大授权的边界。

## 8. 证据与真实性

证据记录：

- 实际命令、退出状态和必要的脱敏输出；
- 修改文件；
- 通过、失败、未运行和受限验证；
- 浏览器、API、CLI 或真实运行表面的手工 QA；
- 清理和回滚结果；
- 制品路径和摘要。

禁止：

- 把未运行测试写成通过；
- 用 fixture 结果冒充真实后端或真机结果；
- 用源码推断冒充运行态事实；
- 把密码、密钥、令牌、Cookie、完整服务器地址、用户数据或原始日志写入
  任务卡、证据和交接。

## 9. 版本与落地

- 区分计划、源码、构建候选、已部署版本和正式发布版本。
- 每个候选绑定摘要、测试结果和适用环境。
- 部署前只读预检，部署前建立可恢复备份，部署后检查真实运行表面。
- 回滚和清理必须在任务卡内预先定义。
- 完整交付包至少包含安装/升级/回滚说明、使用教程、制品摘要和已知限制。
- 未验证的平台、系统或客户端必须标记为 `NOT_RUN`，不得写成兼容。

## 10. 完成汇报

每个获批任务结束时，最终回复和角色交接同时列出：

1. 本次完成内容；
2. 实际验证、失败和 `NOT_RUN`；
3. 当前项目总进度；
4. 下一步任务及执行顺序；
5. 每项下一步的审批状态。

下一步至少区分 `无需审批`、`等待批准`、`已批准未执行`、`已完成` 和
`受阻`。当前任务获批不自动批准清单中的下一项。
