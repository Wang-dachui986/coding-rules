# 需求问答模型

## 1. 模式选择

治理初始化结束后，只提供以下两个模式，并一次只问用户选择哪一个；若用户在
调用时已经明确模式，不重复询问。

- `LIGHT`：轻量项目。用最少问题确认目标、范围、现状、验收和执行限制。
- `FULL`：大型项目。详细确认用户、流程、功能、数据、接口、非功能需求、
  环境、发布、风险和验收。

模式控制问题深度，不降低安全、审批、真实性或验收要求。用户可以随时切换；
切换后保留已经确认的答案。

## 2. 项目上下文

### 空项目

项目中没有有意义的代码、配置、资产、测试或开发文档时，直接从项目目标开始
正常问答，不猜测技术栈或功能。

### 已有项目

先扫描非秘密项目树，读取 `AGENTS.md`、README、设计/需求/架构/路线图、任务
和交接文档，以及与请求直接相关的清单、配置和源码入口。忽略 VCS、缓存、
构建产物、编辑器/系统元数据和秘密形态文件。

问答前先向用户简要返回：

1. 已验证的现状；
2. 文档与实现缺口；
3. 可非破坏补齐的内容；
4. 需要用户决定的调整建议。

不得修改项目，也不得重复询问文件已经明确回答的问题。

## 3. 单问题协议

- 每个助手回复最多提出一个问句；禁止把多个问题用列表、顿号或“以及”合并。
- 用户回答后先吸收其中全部事实，再选择当前最高影响、仍未知的一个问题。
- 优先顺序：阻塞性决定、安全/数据风险、范围边界、验收、依赖、实现偏好。
- 用户暂时不知道时记录为 `UNKNOWN`；若不影响计划可保留，影响计划则继续
  追问或提出一个明确默认值供确认。
- 问答阶段不编制执行任务卡、不修改产品、不运行测试或外部操作。

## 4. 95% 需求覆盖门槛

按下列权重维护需求覆盖率；有验证答案或经用户确认的 `NOT_APPLICABLE` 才得分。

| 维度 | 权重 |
|---|---:|
| 目标与可观察结果 | 15 |
| 用户与核心场景 | 10 |
| 范围与明确排除项 | 15 |
| 现有项目状态与可复用资产 | 10 |
| 功能需求与关键流程 | 15 |
| 数据、接口与外部依赖 | 10 |
| 安全、性能、可靠性与合规 | 10 |
| 环境、部署与兼容范围 | 5 |
| 验证、验收与完成定义 | 5 |
| 风险、审批与操作边界 | 5 |

只有同时满足以下条件才能结束问答：

- 总覆盖率至少 `95%`；
- 目标、范围、完成定义、安全/审批边界和阻塞依赖全部已知；
- 没有会改变架构、数据模型、交付范围或风险等级的未决问题。

`LIGHT` 允许用确认过的 `NOT_APPLICABLE` 快速覆盖无关维度；`FULL` 必须逐项
获得足以制定模块计划的事实。不得用主观“已经差不多”替代覆盖计算。

## 5. 计划审阅闸门

达到门槛后，先返回需求理解摘要、覆盖率、剩余非阻塞未知项、建议方案、范围、
里程碑、验收和风险，形成 `WAITING_REVIEW` 计划。用户批准精确计划前不得生成
执行授权、分发任务或开始产品工作。

用户批准后，R0 才按项目治理规则生成任务卡、预检、请求精确任务批准并执行。
若用户明确要求“本任务结束后停止、不编制下一卡”，完成当前接收与交接后
停止，不自动产生后续任务卡。
